# Decisions

**Shape of the app.** I used one Express server with static HTML, CSS, and browser JavaScript, backed by MongoDB Atlas. This is intentionally small: there is no frontend build pipeline, no ORM, and no separate API service to operate. MongoDB is still a real persisted database and makes it natural to store the nested, configuration-driven question structure. A session cookie stored in MongoDB protects the owner endpoints and page; it is enough for this exercise, while a production system would add password hashing, rate limiting, CSRF protection, and role management.

**Configuration contract.** Public UI first loads `GET /api/config`, then renders whichever active questions it receives. It does not contain estimator questions, options, limits, or prices in its source. The owner edits the same persisted document. Saving creates the next configuration version and replaces the document atomically, so an estimator already holding the older version can continue its screen flow while a new estimate is always validated and calculated against the current stored configuration.

**Formula.** The server finds the selected material, pitch, layers, and stories options in the saved configuration. Material cost is roof area × material rate × (1 + waste factor). Tear-off is roof area × tear-off rate. I add those, multiply by pitch and stories multipliers, then add the flat permit fee. The returned low and high figures are the resulting midpoint reduced and increased by the configured range-spread percentage, rounded to whole dollars. The submitted answers are validated against the active configuration before this calculation runs.

**Seed data.** I normalized the string multiplier (`"1.12"`) to a numeric value. Historical lead `ld_0917` refers to retired material/question keys, so it is preserved exactly as historical evidence rather than forced to match the current configuration. Its given historical estimate is not recalculated. The current configuration starts at version 3; each owner save increments the version for auditability on future leads.

**Scope choices.** I did not build user invitation flows, granular permissions, question creation/reordering, CSV export, webhooks, config-history browsing, or automated tests. They are sensible next features, but the core journey—runtime config, protected editing, server-side calculation, and captured leads—is complete and easy to demonstrate. With another week, I would add server calculation tests, config snapshot history, CSV export, a safer owner-user model, editing validation with field-level server errors, and a production deployment pipeline.
